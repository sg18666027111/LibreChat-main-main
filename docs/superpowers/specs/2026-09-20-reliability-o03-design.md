# O03：用量漏记恢复方案（架构已确认）

目标：聊天或图片业务完成后，用量写入失败可被发现、可在重启后补记；补记只更新统计账本，不调用供应商、不重复扣减用户余额。当前仅完成调查和隔离复现，尚未修改产品代码或生产配置。

## 方案比较

| 方案 | 能覆盖的故障 | 局限 |
| --- | --- | --- |
| 仅增加告警和内存重试 | 进程存活期间的短时错误 | 进程退出后丢失，不能关闭完整 O03 |
| Mongo 补记队列 + 已有业务源扫描 | 已持久化 job/transaction 对应的漏账 | 数据库整体不可写时，补记队列本身也不可写；没有完整源记录的调用仍有缺口 |
| **推荐：私有持久化用量投递日志 + 已有业务源对账** | 已捕获用量在 Mongo 故障、进程重启后的恢复 | 新增私有卷及恢复组件，需要验证容量、权限、崩溃恢复和平台挂载持久性 |

生产当前的单机 Mongo 不能直接采用跨文档事务 outbox。Mongo 官方说明：[事务生产约束](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/)。不把升级 Mongo 拓扑加入本次范围。

## 推荐设计

### 1. 捕获与持久保存

统一图片、批量、聊天、LLM 助手和现有事务镜像的用量投递入口。输入保留稳定 usageEventId、来源标识、用户/租户归属、事件发生时间、供应商/模型、token/图片数量、业务状态、价格证据和事件版本。

用量投递先持久化到专用私有卷，再尝试写 Mongo 统计账本。只有完整记录及必要文件系统同步完成后，才能返回“已持久接收”；“已持久接收”和“已写账本”必须是不同状态。APIMart 的 usageRecorded 不得再以空返回值或单纯未抛错作为成功依据。

建议挂载 `/app/var/usage-delivery`，不在任何静态资源目录下。初始申请 1 GiB，应用待处理数据上限建议 256 MiB，单事件上限 32 KiB；数值在实施前结合实际事件体积验证。新增卷的存储类型、实际容量与费用在生产配置前核实，当前不创建、不购买资源。

只保留补账必要字段，metadata 使用白名单；不落提示词、聊天正文、图片内容、图片签名 URL、API Key、Cookie。账号删除后的补记不能重新关联已删除身份，须与现有匿名化逻辑一致。

### 2. 有界投递与重复保护

用量投递 worker 只接触日志和账本写入函数，不依赖 provider adapter、图片 submit 或用户余额方法。固定小批次、有限并发、退避重试；接入现有 shutdown drain。进程中断后允许重复投递，但账本必须幂等。

幂等以“来源 + 稳定事件 ID + 已持久化版本”为依据；相同重放不增加账目，旧 submitted/unknown 不能覆盖已完成的 succeeded 或更新版本。同状态的修订也要有明确版本顺序，不能仅依靠状态优先级。账本确认后才确认投递；确认丢失时重复投递应得到同一结果。

绑定事件原始发生时间及可证实的价格快照，不能按补记当天价格重新计算。原始价格或状态证据不足的记录进入人工核对状态，不伪造“实际账单”。金额精度改革仍属于 R04。

### 3. 业务源对账

APIMart、批量、Image Egress 和 Transaction 使用已有持久化记录核对“终态已存、用量未存”的窗口。对账只生成用量投递，不重新执行图片任务或扣余额。适配器需要证明同一调用在 job、batch 和 transaction 间的对应关系，不能将多份业务记录重复计费。

新版本后的事件默认进入恢复机制。已有历史记录先产出只读差异报告，明确缺失、已存在、证据不足和超出保留期四类；未经确认不批量补写历史数据，不处理 H01 的 provider 未知结果，不自动重提交。

### 4. 容量、损坏与告警

记录投递失败计数、待处理数量/字节数、最老待处理时长、恢复次数和隔离记录数，接入现有 Prometheus/飞书链路。标签采用固定类别，不放用户 ID、事件 ID、提示词或错误原文。

已确认记录按保留策略清理；未确认记录不得静默删除。达到容量阈值、日志不可写或损坏时明确告警；用量恢复组件不影响登录和只读操作。不能再可靠记录的新付费请求应在供应商调用前受控拒绝；已经接受的调用保留现有业务结果，不能引导用户盲目重试付费操作。具体请求入口和在途容量预留需要在实施计划中逐项列出。

当前部署为单实例 Recreate。卷访问模式并不自动保证只有一个写进程；需明确单写者保护、进程崩溃后的锁恢复和未来副本数增加时的拒绝/迁移行为。[Kubernetes 持久卷访问模式](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)

## 实施阶段与验收门槛

1. **修复确认语义与建立指标**：APIMart 失败不标记成功；统一投递结果契约，覆盖绕开 UsageLedgerService 的入口；先建立失败回归和调用路径清单。本阶段单独完成不能宣称 O03 全部关闭。
2. **实现持久投递与账本幂等**：私有日志、受限重试、顺序/版本保护、清理与 shutdown；接入所有适用入口，复用现有源记录恢复能力。
3. **验证补记和对账**：真实隔离 MongoDB + 子进程测试，覆盖断连后恢复、强制退出、账本已写但确认未写、重复重放、乱序版本、坏记录、磁盘满、身份删除、价格变化、source/ledger 之间崩溃。检查余额不变、provider 调用次数不增加。历史对账只 dry-run。
4. **生产部署与验收**：CI、独立审查、固定镜像验收；确认平台持久挂载后发布。生产仅做健康、权限、空队列/指标和配置验收；通过隔离 canary 证明重启后恢复，不断开生产 Mongo，不发送真实付费请求，不自动补写历史账目。

完成标准：上述各入口有对应的测试和部署证据，恢复日志可跨重启保留，已接收事件不因单次数据库故障丢失，重复投递不重复统计或扣费，告警链路有效，临时资源清理完成。

## 边界

该方案保证的是“已捕获并持久接收的用量事件”的恢复。供应商已计费但尚未返回可捕获用量、随后进程/主机丢失的情形，仍需供应商对账；不能从内部成功数推出供应商账单完整。节点磁盘整体丢失也不是同机 PVC 的保护范围。

用户于 2026-09-20 回复“是”，已确认本方案的架构和新增私有卷方向。具体实施计划另行评审；存储类型、容量和实际费用须在资源创建前核实。本次批准不包含历史数据批量补写。产品代码、依赖、数据库、生产挂载尚未修改。
